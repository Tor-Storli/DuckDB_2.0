Here is a full trigger demo script on your financial data. Run it in a database with the 2.0 storage format. I couldn’t run it myself, since I have no DuckDB 2.0 here. It follows the CREATE TRIGGER docs and ties back to your VARIANT video.

What the docs say 2.0 triggers can do
Timing: BEFORE and AFTER only. There is no INSTEAD OF and no triggers on views.
Events: INSERT, UPDATE and DELETE, with UPDATE OF col to limit an update trigger to specific columns.
Granularity:
FOR EACH ROW exposes NEW or OLD. It works for INSERT and DELETE only.
FOR EACH STATEMENT fires once per statement and can use transition tables (REFERENCING OLD TABLE AS o NEW TABLE AS n).
Multiple triggers: several triggers on one event fire in creation order.
The body: a single SQL statement. The docs don’t mention a WHEN clause.

Because row-level and statement-level triggers can’t be mixed on the same event of a table, I use two tables:

zscore_live has statement-level triggers.
zscore_rows has row-level triggers.

{SQL}
-------------------------------------------------------------

------------------------------------------------------------
-- 0. SETUP (work on copies, leave zscore_inputs untouched)
------------------------------------------------------------
CREATE OR REPLACE TABLE zscore_live
(ticker VARCHAR, 
 period_end DATE, 
 ebit DOUBLE, 
 revenue DOUBLE, 
 retained_earnings DOUBLE, 
 total_liabilities DOUBLE,
 ebit_margin DOUBLE
 );

INSERT INTO zscore_live
SELECT ticker, period_end, ebit, revenue, retained_earnings, total_liabilities,
       ebit / revenue AS ebit_margin
FROM read_json('c:/tmp/zscore_inputs.json');

FROM zscore_live LIMIT 10;
 
CREATE OR REPLACE TABLE zscore_rows AS FROM zscore_live LIMIT 0;  -- row-level demos

-- Audit destinations. details is a VARIANT, so any shape fits
CREATE OR REPLACE TABLE change_log (ts TIMESTAMP, table_name VARCHAR, event VARCHAR, details VARIANT);
CREATE OR REPLACE TABLE ebit_changes (ts TIMESTAMP, ticker VARCHAR, period_end DATE, old_ebit DOUBLE, new_ebit DOUBLE);
  
CREATE OR REPLACE TABLE insert_counter (ts TIMESTAMP, total_rows BIGINT);
CREATE OR REPLACE TABLE zscore_archive AS FROM zscore_live LIMIT 0;
CREATE OR REPLACE TABLE row_log (ts TIMESTAMP, event VARCHAR, ticker VARCHAR, period_end DATE);
CREATE OR REPLACE TABLE quarantine (ts TIMESTAMP, ticker VARCHAR, period_end DATE, reason VARCHAR);

------------------------------------------------------------
-- 1. AFTER INSERT, FOR EACH STATEMENT + NEW TABLE (batch summary)
------------------------------------------------------------
CREATE TRIGGER trg_ins_summary
AFTER INSERT ON zscore_live
REFERENCING NEW TABLE AS n
FOR EACH STATEMENT
  INSERT INTO change_log
  SELECT now(), 'zscore_live', 'INSERT',
         {'rows': count(*), 'tickers': list(DISTINCT ticker)}::VARIANT
  FROM n;

-- 1b. Second trigger, same event: fires AFTER the first, in creation order
CREATE TRIGGER trg_ins_counter
AFTER INSERT ON zscore_live
FOR EACH STATEMENT
  INSERT INTO insert_counter SELECT now(), count(*) FROM zscore_live;

INSERT INTO zscore_live (ticker, period_end, total_liabilities, retained_earnings, ebit, revenue)
VALUES ('HSY','2025-12-31', 8.5e9, 6.0e9, 3.0e9, 11.5e9),
       ('KHC','2025-12-27', 38.0e9, 2.4e9, 1.9e9, NULL);

SELECT * FROM change_log;       -- {'rows': 2, 'tickers': [HSY, KHC]}
SELECT * FROM insert_counter;   -- one row per statement, not per inserted row

------------------------------------------------------------
-- 2. AFTER UPDATE + OLD/NEW TABLE, audit stored as VARIANT
--    (join key is ticker+period_end, since the table has no PK)
------------------------------------------------------------
CREATE TRIGGER trg_upd_audit
AFTER UPDATE ON zscore_live
REFERENCING OLD TABLE AS o NEW TABLE AS n
FOR EACH STATEMENT
  INSERT INTO change_log
  SELECT now(), 'zscore_live', 'UPDATE',
         {'ticker': n.ticker, 'period_end': n.period_end::VARCHAR,
          'old': {'ebit': o.ebit, 'revenue': o.revenue},
          'new': {'ebit': n.ebit, 'revenue': n.revenue}}::VARIANT
  FROM o JOIN n ON o.ticker = n.ticker AND o.period_end = n.period_end;

-- 2b. Column-restricted trigger: fires only when ebit is in the SET list.
--     No REFERENCING allowed here, so it can't see old/new rows, only that it ran.
CREATE OR REPLACE TABLE ebit_changes (
  ts TIMESTAMP, event VARCHAR, rows_in_table BIGINT, total_ebit DOUBLE);

CREATE OR REPLACE TRIGGER trg_ebit_only
AFTER UPDATE OF ebit ON zscore_live
FOR EACH STATEMENT
  INSERT INTO ebit_changes
  SELECT now(), 'ebit column updated', count(*), sum(ebit) FROM zscore_live;

-- Test: first update does NOT touch ebit, second does
UPDATE zscore_live SET revenue = revenue * 1.01 WHERE ticker = 'HSY';  -- trg_upd_audit fires, trg_ebit_only does NOT
SELECT count(*) AS should_be_0 FROM ebit_changes;

UPDATE zscore_live SET ebit = ebit * 1.10 WHERE ticker = 'GIS';        -- both fire
SELECT * FROM ebit_changes;                                            -- 1 row: a post-update snapshot

SELECT count(*) FROM ebit_changes;
-- Query the VARIANT audit trail
SELECT ts,
       details.ticker AS ticker,
       (details.old.ebit)::DOUBLE AS old_ebit,
       (details.new.ebit)::DOUBLE AS new_ebit,
       (details.new.ebit)::DOUBLE - (details.old.ebit)::DOUBLE AS delta
FROM change_log
WHERE event = 'UPDATE' AND variant_exists(details, 'old')
ORDER BY ts;

------------------------------------------------------------
-- 3. BEFORE + AFTER DELETE, statement-level (snapshot + archive)
------------------------------------------------------------
CREATE TRIGGER trg_before_delete
BEFORE DELETE ON zscore_live
FOR EACH STATEMENT
  INSERT INTO change_log
  SELECT now(), 'zscore_live', 'BEFORE DELETE', {'rows_before': count(*)}::VARIANT
  FROM zscore_live;

CREATE TRIGGER trg_archive
AFTER DELETE ON zscore_live
REFERENCING OLD TABLE AS o
FOR EACH STATEMENT
  INSERT INTO zscore_archive SELECT * FROM o;

DELETE FROM zscore_live WHERE revenue IS NULL;

SELECT count(*) AS archived FROM zscore_archive;
SELECT * FROM change_log WHERE event = 'BEFORE DELETE';

------------------------------------------------------------
-- 4. RETURNING works because zscore_live has only statement-level triggers
------------------------------------------------------------
INSERT INTO zscore_live (ticker, period_end, ebit, revenue)
VALUES ('GIS','2026-11-30', 1.0e9, 19.0e9)
RETURNING ticker, period_end;

------------------------------------------------------------
-- 5. ROW-LEVEL triggers on zscore_rows (NEW / OLD)
------------------------------------------------------------
CREATE TRIGGER trg_row_ins
AFTER INSERT ON zscore_rows
FOR EACH ROW
  INSERT INTO row_log VALUES (now(), 'INSERT', NEW.ticker, NEW.period_end);

-- 5b. No WHEN clause in the docs, so use WHERE inside the body (conditional trigger).
CREATE TRIGGER trg_row_quarantine
AFTER INSERT ON zscore_rows
FOR EACH ROW
  INSERT INTO quarantine
  SELECT now(), NEW.ticker, NEW.period_end, 'missing revenue'
  WHERE NEW.revenue IS NULL;

CREATE TRIGGER trg_row_del
AFTER DELETE ON zscore_rows
FOR EACH ROW
  INSERT INTO row_log VALUES (now(), 'DELETE', OLD.ticker, OLD.period_end);

INSERT INTO zscore_rows (ticker, period_end, ebit, revenue)
VALUES ('GIS','2026-05-31', 885.8e6, 18424.6e6),
       ('KHC','2024-12-28', 1683e6, NULL),
       ('HSY','2024-12-31', 2898.2e6, 11202.3e6);

SELECT * FROM row_log;      -- 3 INSERT rows, one per row
SELECT * FROM quarantine;   -- only the KHC row

DELETE FROM zscore_rows WHERE ticker = 'HSY';
SELECT * FROM row_log WHERE event = 'DELETE';

------------------------------------------------------------
-- 6. Inspect, replace, drop
------------------------------------------------------------
SELECT trigger_name, table_name, action_timing, event_manipulation, for_each
FROM duckdb_triggers() ORDER BY table_name, trigger_name;

CREATE OR REPLACE TRIGGER trg_ins_counter     -- redefine in place
AFTER INSERT ON zscore_live
FOR EACH STATEMENT
  INSERT INTO insert_counter SELECT now(), count(DISTINCT ticker) FROM zscore_live;

CREATE TRIGGER IF NOT EXISTS trg_ins_counter  -- silently does nothing
AFTER INSERT ON zscore_live
FOR EACH STATEMENT
  INSERT INTO insert_counter VALUES (now(), -1);

DROP TRIGGER trg_ebit_only ON zscore_live;
DROP TRIGGER IF EXISTS trg_nope ON zscore_live;

“Gotchas” segment

These are the 2.0 limitations from the docs. Each statement should fail, so run them one at a time on camera:

{SQL}
---------------------------------------------
-- BEFORE ... FOR EACH ROW is not supported
CREATE TRIGGER bad1 BEFORE INSERT ON zscore_rows FOR EACH ROW INSERT INTO row_log VALUES (now(),'x',NEW.ticker,NEW.period_end);

-- UPDATE ... FOR EACH ROW is not supported
CREATE TRIGGER bad2 AFTER UPDATE ON zscore_rows FOR EACH ROW INSERT INTO row_log VALUES (now(),'x',NEW.ticker,NEW.period_end);

-- Can't mix ROW and STATEMENT for the same event on one table
CREATE TRIGGER bad3 AFTER INSERT ON zscore_live FOR EACH ROW INSERT INTO row_log VALUES (now(),'x',NEW.ticker,NEW.period_end);

-- INSTEAD OF / triggers on views are not supported
CREATE VIEW v AS FROM zscore_live;
CREATE TRIGGER bad4 INSTEAD OF INSERT ON v FOR EACH ROW INSERT INTO zscore_live SELECT NEW.*;

-- MERGE INTO and upsert variants fail on tables with UPDATE/DELETE triggers
INSERT OR REPLACE INTO zscore_live SELECT * FROM zscore_live LIMIT 1;
INSERT INTO zscore_live SELECT * FROM zscore_live LIMIT 1 ON CONFLICT DO NOTHING;

-- RETURNING is not allowed on tables with row-level triggers
INSERT INTO zscore_rows (ticker, period_end) VALUES ('X','2026-01-01') RETURNING ticker;

Things to watch when you run it
Storage version: if CREATE TRIGGER complains about the database’s storage version, use the ATTACH ... (STORAGE_VERSION 'latest') fix from earlier.
Untested spots:
The nested struct cast to VARIANT in trigger 2.
INSERT ... SELECT ... WHERE NEW.revenue IS NULL with no FROM in trigger 5b. If DuckDB rejects it, use FROM (SELECT 1) WHERE ....
NEW.* in the view example. That one is meant to fail anyway.
Duplicate keys: your table has no primary key. If two rows share ticker and period_end, the join in trigger 2 would produce duplicate audit rows. Real data from your table should be unique per period.
Cleanup: DROP TABLE the demo tables when you’re done. Dropping a table also drops its triggers.
Other angles: duckdb_triggers() and the VARIANT audit query make good screen moments. If you want more, a rollup table maintained by a statement-level trigger or a Z-score recompute on insert would also work.
